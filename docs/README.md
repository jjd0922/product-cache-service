# Product Cache Service

상품 조회 성능과 운영 안정성을 함께 고려해 설계한 멀티 모듈 기반 백엔드 서비스다.

단순 CRUD 구현에 머무르지 않고, 실제 운영 환경에서 자주 마주치는 캐시 유실, 재적재, 부분 장애, 테스트 분리 같은 문제를 어떻게 구조적으로 해결할지에 초점을 맞췄다.

## 프로젝트 목표

- 반복 조회가 많은 상품 API의 성능 개선
- 운영 가능한 Redis 캐시 구조 설계
- 멀티 모듈 기반 책임 분리
- 테스트 가능한 구조 확보

## 주요 구현 내용

- Redis 기반 상품 캐시 조회
- detail cache / runtime cache 분리
- Cache-Aside 기반 DB fallback
- cache miss 시 누락 캐시 self-healing
- 관리자용 캐시 재구축 API
- 재구축 중복 실행 방지 및 요청 제한
- 진행률, 활성 여부, 실패 사유를 포함한 상태 조회
- 계층별 테스트 분리
- Testcontainers 기반 Redis 통합 테스트

- 입력값 검증
- 예외 응답 변환

- detail/runtime 캐시 병합 조회
- cache miss 시 DB fallback

## 캐시 전략

이 프로젝트는 상품 캐시를 하나로 관리하지 않고, 데이터 성격에 따라 분리했다.

### detail cache

상품명, 가격, 기본 정보처럼 상대적으로 정적인 데이터를 저장한다.

### runtime cache

판매 상태, 품절 여부처럼 더 자주 변하는 상태성 데이터를 저장한다.

이렇게 분리하면 작은 상태 변경에도 전체 캐시를 다시 갱신하지 않아도 되므로, 갱신 범위를 줄이고 운영 유연성을 높일 수 있다.

## 조회 전략

조회 흐름은 Cache-Aside를 기반으로 구성했다.

1. detail cache와 runtime cache를 조회한다.
2. 둘 다 존재하면 병합 후 응답한다.
3. 하나라도 없으면 DB fallback을 수행한다.
4. 조회 결과를 응답으로 반환한다.
5. 누락된 캐시는 다시 적재한다.

즉, 단순 cache miss 처리에서 끝나지 않고, 부분 유실 상태를 자동 복구하는 self-healing 구조를 적용했다.

## 운영 기능

운영자가 직접 캐시를 제어할 수 있도록 재구축 기능을 설계했다.

- 캐시 재구축 요청
- 작업 ID 기반 상태 조회
- 진행률 확인
- 활성 작업 여부 확인
- 실패 사유 확인
- 중복 실행 방지
- 요청 수 제한

이를 통해 캐시를 단순 성능 보조 수단이 아니라 운영 가능한 데이터 계층으로 다루도록 했다.

## 테스트 전략

테스트는 계층별 책임에 맞게 분리했다.

### 도메인 테스트

- 상품 상태 계산
- 판매 가능 여부 판단

### 애플리케이션 테스트

- 캐시 병합 조회
- DB fallback
- self-healing 재적재
- 재구축 요청 및 상태 조회 흐름 검증

### 인프라 테스트

- Redis 저장/조회/삭제
- 직렬화/역직렬화
- 예외 대응

### JPA 테스트

- 저장
- 조회
- 매핑
- 제약조건 검증

### Testcontainers 통합 테스트

실제 Redis 컨테이너를 띄워 아래 항목을 검증했다.

- 실제 Redis 저장
- 실제 Redis 조회
- TTL 적용
- key 삭제

## 설계 포인트

이 프로젝트에서 중요하게 본 것은 기능 구현 자체보다 다음과 같은 설계 기준이다.

- 성능 문제를 캐시 구조로 해결할 것
- 운영 이슈까지 고려한 구조를 만들 것
- 흐름 제어와 비즈니스 규칙, 기술 구현을 분리할 것
- 테스트를 통해 설계 의도를 검증 가능하게 만들 것

## 개선 가능 포인트

- 대량 재구축 최적화
- 이벤트 기반 캐시 갱신
- hit/miss, fallback, 처리 시간 등 메트릭 수집
- TTL 및 부분 무효화 정책 고도화
- 다중 인스턴스 환경용 job store 확장
